## 1. Назначение

ALXPRGS Workspace — легковесная self-hosted платформа предоставления изолированных вычислительных пространств для искусственного интеллекта посредством Model Context Protocol (MCP).

Первоначальная цель проекта — устранение ограничений встроенной среды исполнения ChatGPT, препятствующих полноценной разработке, компиляции, тестированию и проверке программного обеспечения.

Сервис должен предоставлять модели возможность самостоятельно подготавливать вычислительное окружение, работать с исходным кодом, выполнять команды, анализировать ошибки, проводить тестирование и возвращать пользователю проверенные результаты.

Основной приоритет проекта — минимальное потребление ресурсов устройства, на котором развёрнут сервис.

## 2. Принципы разработки

- Простота архитектуры и эксплуатации.
- Минимальное потребление системных ресурсов.
- Безопасность по умолчанию.
- Воспроизводимость вычислительных окружений.
- Независимость от конкретной языковой модели.
- Соответствие официальной документации OpenAI и спецификации MCP.
- Совместимость с существующей инфраструктурой ALXPRGS.
- Минимизация количества внешних зависимостей.
- Отсутствие необязательных инфраструктурных компонентов.
- Расширяемость без преждевременного усложнения архитектуры.
- Приоритет подтверждённой работоспособности над количеством реализованных функций.

## 3. Целевой сценарий

Пользователь предоставляет ChatGPT техническое задание и исходные файлы проекта.

ChatGPT посредством MCP:

1. Получает сведения о доступных ресурсах сервера.
2. Получает каталог доступных возможностей.
3. Создаёт рабочее пространство с необходимыми инструментами.
4. Импортирует исходные файлы.
5. Изучает существующий проект.
6. Проверяет исходную сборку.
7. Вносит необходимые изменения.
8. Компилирует проект и запускает тесты.
9. Анализирует ошибки.
10. Исправляет обнаруженные проблемы и повторяет проверки.
11. Выполняет итоговую приёмку.
12. Формирует архив с результатом.
13. Публикует артефакт для скачивания.
14. Останавливает рабочее пространство.

Основной сценарий должен выполняться через обычный веб-интерфейс ChatGPT без обязательного использования Agent Mode, Work, Codex или локального клиента.

Ограничения продолжительности диалога, количества вызовов инструментов и подтверждений действий определяются MCP-клиентом и не должны обходиться сервисом.

## 4. Поддерживаемые платформы

Workspace Server должен нативно собираться и запускаться на:

- Linux x86-64.
- Windows x86-64.

В версии 0.1.0 поддерживаются Linux-контейнеры на обеих платформах.

### 4.1. Linux

Используется Docker Engine с rootless-исполнением.

Обязательные ограничения ресурсов должны обеспечиваться посредством поддерживаемых механизмов Docker, cgroups v2 и операционной системы.

### 4.2. Windows

Используется Docker с Linux backend на базе WSL2.

Workspace Server должен работать как нативное Windows-приложение и взаимодействовать с поддерживаемым Docker runtime.

Не допускается создание отдельной виртуальной машины для каждого пространства.

Все Linux-контейнеры одного развёртывания могут использовать общий Linux backend.

### 4.3. Ограничения

При отсутствии Docker, WSL2, необходимой поддержки ядра или обязательных механизмов изоляции сервис должен возвращать диагностическую ошибку.

Выполнение произвольных пользовательских команд непосредственно на хосте запрещено.

Нативные Windows-контейнеры, Podman и дополнительные Runtime Providers не входят в обязательный объём версии 0.1.0.

## 5. Архитектура

Workspace представляет собой самостоятельное приложение на Rust.

Основные логические компоненты:

- MCP Server.
- HTTP API.
- Authentication.
- Workspace Manager.
- Docker Runtime.
- Capability Registry.
- Job Manager.
- File Service.
- Artifact Service.
- Resource Manager.
- Web Administration.
- CLI Administration.
- Audit Service.

Компоненты должны быть разделены программно, но не требуют развёртывания в качестве отдельных микросервисов.

Метаданные хранятся в SQLite.

Рабочие файлы, артефакты и логи хранятся в локальной файловой системе.

Обязательное использование PostgreSQL, Redis, Kubernetes, RabbitMQ и внешнего объектного хранилища не предусматривается.

В первой версии выполнение заданий осуществляется на устройстве, на котором развёрнут Workspace Server.

## 6. Независимые развёртывания

Поддерживается развёртывание нескольких независимых экземпляров ALXPRGS Workspace.

Каждый экземпляр имеет собственные:

- Идентификатор.
- Конфигурацию.
- HTTP и MCP endpoints.
- Базу данных.
- Рабочие пространства.
- Файловое хранилище.
- Ограничения ресурсов.
- OAuth-клиенты.
- Ключи авторизации.
- Журналы операций.

Несколько экземпляров могут использовать один ALXPRGS SSO.

При размещении нескольких экземпляров на одном устройстве должны исключаться конфликты портов, имён контейнеров, Docker networks и volumes.

Совокупное потребление ресурсов всех экземпляров должно ограничиваться средствами хоста либо явно распределёнными административными бюджетами.

Распределённый кластер вычислительных узлов не входит в MVP.

## 7. Рабочие пространства

Workspace представляет собой логически изолированное вычислительное окружение с уникальным идентификатором.

Каждое пространство содержит:

- Уникальный идентификатор.
- Имя.
- Идентификатор владельца.
- Набор подключённых возможностей.
- Конфигурацию сетевого доступа.
- Ограничения ресурсов.
- Рабочую директорию.
- Список заданий.
- Время создания.
- Время последней активности.
- Срок хранения.
- Признак закрепления.
- Текущее состояние.

Поддерживается создание нескольких независимых пространств в рамках одного экземпляра сервиса.

Создание пространства не должно требовать постоянного резервирования всей выделенной памяти.

Пространство может существовать без запущенного контейнера.

### 7.1. Состояния пространства

- `created` — конфигурация создана.
- `starting` — выполняется запуск контейнера.
- `running` — контейнер запущен.
- `idle` — контейнер запущен, активные задания отсутствуют.
- `stopping` — выполняется остановка.
- `stopped` — контейнер остановлен, файлы сохранены.
- `failed` — обнаружена ошибка окружения.
- `deleting` — выполняется удаление.
- `expired` — истёк срок хранения.

### 7.2. Повторный запуск

При повторном обращении к остановленному пространству сервис должен автоматически восстановить вычислительное окружение.

Рабочие файлы, конфигурация и доступные журналы должны сохраняться.

Состояние оперативной памяти и ранее запущенных процессов не сохраняется.

## 8. Жизненный цикл и хранение

Для каждого пространства устанавливается TTL.

Предлагаемый срок хранения по умолчанию — 24 часа с момента последней активности.

Пользователь может:

- Продлевать срок хранения.
- Закреплять пространство.
- Снимать закрепление.
- Останавливать пространство.
- Удалять пространство.

Закреплённое пространство не удаляется автоматически по TTL.

Закрепление не отменяет:

- Ограничения CPU и RAM.
- Ограничения дискового пространства.
- Автоматическую остановку контейнера.
- Ограничения времени выполнения заданий.
- Административные ограничения сервера.

Контейнер автоматически останавливается после истечения настраиваемого периода отсутствия активных заданий.

Предлагаемое значение по умолчанию — 300 секунд.

Пространство с выполняющимся заданием не считается простаивающим.

Просроченные незакреплённые пространства удаляются автоматически.

При приближении к лимиту дискового пространства сервис должен отклонять новые операции либо инициировать предусмотренную политикой очистку.

Закреплённые пространства не удаляются автоматически без явного административного разрешения.

## 9. Capabilities

Capabilities представляют собой каталог доступных инструментов и вычислительных возможностей.

Перед созданием пространства MCP-клиент должен иметь возможность получить список поддерживаемых возможностей.

### 9.1. Обязательные модули

| ID | Состав |
|---|---|
| base | Bash, coreutils, find, grep, tar, unzip, curl, CA certificates |
| rust | rustc, Cargo, rustfmt, Clippy |
| cpp | GCC, G++, CMake, Ninja, pkg-config |
| git | Git |
| python | Python, pip, venv |
| ffmpeg | FFmpeg, FFprobe |
| whisper-vad | Whisper.cpp VAD и совместимая модель Silero |

Модуль `base` подключается автоматически.

### 9.2. Метаданные возможностей

Каждая возможность должна содержать:

- Идентификатор.
- Название.
- Описание.
- Версию.
- Список предоставляемых инструментов.
- Зависимости от других возможностей.
- Совместимость.
- Состояние доступности.
- При необходимости — сведения о требуемых сетевых разрешениях.

### 9.3. Реализация

В первой версии допускается использование заранее подготовленных Docker-образов и профилей окружения.

Docker-образы должны использовать общие слои для уменьшения потребления дискового пространства.

Сервер подбирает подходящий профиль на основании запрошенных возможностей.

Если комбинация модулей не поддерживается, сервис возвращает понятную ошибку и сведения о доступных вариантах.

Версии инструментов и моделей должны фиксироваться.

Динамическая установка произвольных привилегированных компонентов хоста через MCP запрещена.

Полноценная система сторонних модулей не входит в MVP.

## 10. Выполнение команд

Workspace должен предоставлять универсальный механизм выполнения команд внутри соответствующего контейнера.

Поддерживаются:

- Команды с аргументами.
- Выполнение shell-скриптов внутри контейнера.
- Выбор рабочей директории.
- Переменные окружения задания.
- Ограничение времени выполнения.
- Получение stdout и stderr.
- Получение кода завершения.
- Получение частичных логов.
- Выполнение длительных процессов.
- Отмена выполняемого задания.

Каждая длительная операция получает уникальный Job ID.

Выполнение задания не должно зависеть от продолжительности отдельного HTTP-запроса или MCP-вызова.

### 10.1. Состояния заданий

- `queued`
- `running`
- `succeeded`
- `failed`
- `cancelled`
- `timed_out`
- `interrupted`

### 10.2. Результаты выполнения

Результат должен содержать:

- Job ID.
- Workspace ID.
- Текущее состояние.
- Код завершения при наличии.
- Продолжительность выполнения.
- Ограниченный объём stdout и stderr.
- Признак наличия дополнительных логов.
- Причину ошибки, отмены или превышения лимита.

Завершение MCP-вызова не считается подтверждением успешного выполнения команды.

### 10.3. Длительные операции

MCP-клиент может получать актуальное состояние задания посредством повторных вызовов инструментов.

Логи должны поддерживать постраничное чтение либо чтение с указанной позиции.

Полная передача больших логов в контекст языковой модели не должна выполняться автоматически.

Повторные запросы создания заданий должны поддерживать защиту от случайного дублирования посредством idempotency keys.

## 11. Работа с файлами

Workspace предоставляет операции:

- Просмотра каталогов.
- Чтения файлов.
- Чтения диапазонов строк.
- Создания файлов.
- Перезаписи файлов.
- Применения патчей.
- Импорта файлов.
- Импорта архивов.
- Загрузки файлов по разрешённым URL.

Все операции ограничиваются рабочей директорией пространства и специально разрешёнными областями хранения.

Для изменения существующих файлов рекомендуется поддерживать проверку ожидаемого хеша или версии файла.

### 11.1. Вложения ChatGPT

Для импорта приложенных пользователем файлов используется документированный механизм OpenAI `_meta["openai/fileParams"]`.

Содержимое бинарных файлов должно передаваться непосредственно по HTTPS, без кодирования полного файла в текстовый контекст модели.

Сервис должен проверять:

- Принадлежность операции авторизованному пользователю.
- Допустимый источник загрузки.
- Максимальный размер файла.
- Безопасность пути назначения.
- Доступность дискового пространства.

Временные ссылки OpenAI не должны сохраняться в открытых логах.

### 11.2. Импорт по URL

Поддерживается загрузка файлов из разрешённых внешних источников.

Применяется сетевая политика Allowlist.

Проверке подлежат первоначальный адрес, перенаправления и фактический адрес назначения.

Загрузка должна поддерживать ограничение размера и времени передачи.

### 11.3. Ручная загрузка

Минимальная веб-панель должна предоставлять возможность загрузки файлов непосредственно в выбранное пространство.

Для загрузки не требуется работающий контейнер.

### 11.4. Безопасность архивов

Распаковка архивов должна защищаться от:

- Path traversal.
- ZIP Slip.
- Выхода за пределы рабочей директории.
- Небезопасных символических и жёстких ссылок.
- Превышения допустимого объёма распакованных данных.
- Чрезмерного количества файлов.

## 12. Артефакты

Файлы, предназначенные для передачи пользователю, публикуются как артефакты.

Каждый артефакт содержит:

- Уникальный идентификатор.
- Идентификатор владельца.
- Идентификатор исходного пространства.
- Имя файла.
- Размер.
- MIME-тип.
- SHA-256.
- Время публикации.
- Срок хранения.

Сервис должен предоставлять временную защищённую ссылку для скачивания опубликованного артефакта.

ChatGPT должен иметь возможность передать полученную ссылку пользователю.

Артефакты хранятся независимо от жизненного цикла контейнера и исходного пространства.

Остановка или удаление пространства не должны удалять опубликованный артефакт до истечения его срока хранения.

Ссылка на артефакт:

- Ограничивается по времени.
- Не предоставляет доступ к другим файлам.
- Может быть отозвана.
- Не раскрывает внутреннюю структуру хранилища.

Предлагаемый срок хранения артефактов по умолчанию — 24 часа.

## 13. Сетевой доступ

Сетевой доступ реализуется на основании Allowlist.

Поддерживаются два режима:

- `none` — внешний сетевой доступ отключён.
- `allowlist` — доступ разрешён только к утверждённым ресурсам.

Режим по умолчанию — `none`.

Allowlist управляется администратором через конфигурацию или веб-панель.

MCP-клиент не может самостоятельно расширять список разрешённых ресурсов.

### 13.1. Разрешённые категории

Для целевого сценария должны поддерживаться разрешения на доступ к:

- Cargo Registry.
- Официальным ресурсам Rust.
- Репозиториям Python.
- Публичным репозиториям GitHub.
- GitHub Releases.
- Репозиториям системных пакетов.
- Разрешённым источникам моделей Whisper и Silero.

Точный список доменов определяется на этапе технической реализации.

### 13.2. Запрещённые ресурсы

Контейнеры не должны иметь доступ к:

- Локальной сети хоста.
- Loopback-интерфейсам хоста.
- Приватным сетевым диапазонам.
- Link-local адресам.
- Cloud metadata endpoints.
- Docker API и Docker socket.
- Управляющим интерфейсам Workspace.
- Внутренним сервисам ALXPRGS.
- Другим вычислительным пространствам.

Сетевая политика должна обеспечиваться техническими механизмами, а не инструкциями для языковой модели.

Необходимо учитывать DNS rebinding, HTTP redirects, IPv4, IPv6 и возможность обхода прокси прямыми соединениями.

При невозможности обеспечить заявленную сетевую изоляцию запуск пространства с сетевым доступом запрещается.

File Service может импортировать авторизованные пользовательские вложения независимо от сетевых разрешений самого контейнера.

Неограниченный публичный интернет не входит в MVP.

## 14. Управление ресурсами

Workspace должен обеспечивать индивидуальные ограничения каждого пространства и глобальные ограничения экземпляра сервиса.

Ограничиваемые ресурсы:

- CPU.
- RAM.
- Swap.
- Дисковое пространство.
- Количество процессов.
- Дисковый ввод-вывод, если поддерживается платформой.
- Время выполнения заданий.
- Количество одновременно активных пространств.
- Количество одновременных ресурсоёмких заданий.
- Размер файлов и логов.

Индивидуальные ограничения не могут превышать глобальные ограничения.

MCP-клиент может запрашивать желаемый объём ресурсов, но окончательное решение принимается сервером.

При недостатке ресурсов новые задания ставятся в очередь или отклоняются с понятным объяснением.

Docker должен использоваться совместно с механизмами операционной системы, необходимыми для фактического обеспечения лимитов.

Одного наличия параметров ограничения в конфигурации недостаточно.

### 14.1. Предварительные настройки ALX-3

| Параметр | Значение |
|---|---|
| Общий CPU | 2 ядра |
| Общая RAM | 4096 МиБ |
| Общее хранилище Workspace | 40 ГиБ |
| Максимум активных пространств | 3 |
| Одновременные тяжёлые сборки | 1 |
| Максимум процессов на пространство | 256 |
| Максимальное время задания | 3600 секунд |
| Остановка при простое | 300 секунд |

| Максимальный размер импортируемого файла | 256 МиБ |

Значения являются предварительными настройками конкретного развёртывания, а не универсальными ограничениями продукта.

Все параметры должны быть настраиваемыми.

Фактический бюджет ресурсов определяется после измерения нагрузки на устройство.

### 14.2. Целевые показатели

- Управляющая часть Workspace должна потреблять минимальное количество памяти и CPU в состоянии простоя.
- Целевое потребление управляющего сервиса — до 100 МиБ RAM в простое.
- Остановленные пространства не должны иметь постоянно работающих вычислительных процессов.
- Инструменты и образы должны переиспользоваться между пространствами.
- Размер логов и кешей должен ограничиваться.
- Workspace не должен создавать неконтролируемую нагрузку на другие сервисы устройства.

Целевые показатели необходимо подтвердить измерениями.

Потребление Docker, WSL2 и других системных компонентов учитывается отдельно и включается в оценку общей нагрузки.

## 15. Авторизация и ALXPRGS SSO

Идентификация пользователя осуществляется через ALXPRGS SSO.

Workspace должен использовать существующий механизм OIDC для входа пользователя.

Реализация Notify используется в качестве архитектурного референса интеграции ChatGPT, OAuth и ALXPRGS SSO.

### 15.1. Подключение MCP-клиентов

Обязательные требования:

- OAuth Authorization Code Flow.
- PKCE S256.
- OAuth discovery.
- Protected Resource Metadata.
- Проверка resource и audience.
- Проверка issuer.
- Точные redirect URI.
- Ограниченные scopes.
- Короткоживущие access-токены.
- Безопасное обновление токенов.
- Отзыв доступа.
- Проверка полномочий при каждом запросе.
- Поддержка статических OAuth Client ID и Client Secret.

OAuth-интеграция должна соответствовать актуальной документации OpenAI и спецификации MCP.

### 15.2. Подключения

Пользователь должен иметь возможность:

- Создавать OAuth-подключения.
- Просматривать действующие подключения.
- Назначать разрешения.
- Отзывать доступ.
- Перевыпускать credentials.

Поддерживаются несколько независимых подключений.

Каждое подключение имеет собственный набор разрешений.

MCP-клиент не может самостоятельно расширять предоставленные полномочия.

### 15.3. Разрешения

Предварительное разделение scopes:

- `workspace:read`
- `workspace:create`
- `workspace:manage`
- `workspace:delete`
- `execution:run`
- `execution:cancel`
- `files:read`
- `files:write`
- `files:import`
- `artifacts:read`
- `artifacts:publish`
- `network:allowlist`

Точный контракт scopes фиксируется в документации MCP.

OAuth-токены SSO, ключи авторизации и секреты сервиса не передаются вычислительным пространствам.

Самостоятельная реализация криптографических примитивов не допускается.

## 19. Безопасность

Workspace является сервисом исполнения потенциально недоверенного кода.

Безопасность является обязательной частью первой версии.

### 19.1. Контейнерная изоляция

Обязательны:

- Непривилегированное исполнение.
- Rootless Docker на Linux.
- Изоляция рабочих пространств.
- Запрет privileged-контейнеров.
- Запрет host network.
- Запрет host PID namespace.
- Запрет доступа к Docker socket.
- Запрет произвольных host mounts.
- Ограничение Linux capabilities.
- Применение поддерживаемых профилей seccomp.
- Использование AppArmor или других поддерживаемых механизмов защиты.
- Read-only root filesystem, за исключением специально разрешённых областей записи.

### 19.2. Изоляция данных

Контейнерам запрещён доступ к:

- Домашним директориям пользователя хоста.
- SSH-ключам.
- OAuth credentials.
- Секретам ALXPRGS SSO.
- Конфигурации production-сервисов.
- Базам данных хоста.
- Файлам других пространств.

Проверка путей и полномочий должна выполняться при каждой файловой операции.

### 19.3. Управление полномочиями

Любые инструкции, содержащиеся в исходных файлах, документации, выводе команд или внешних ресурсах, не могут изменять политику безопасности пространства.

MCP-клиент не может:

- Получить дополнительные scopes самостоятельно.
- Повысить установленные лимиты.
- Изменить Allowlist.
- Запросить privileged-контейнер.
- Подключить произвольную директорию хоста.
- Получить доступ к управляющим интерфейсам.

### 19.4. Аварийная остановка

Администратор должен иметь возможность прекратить выполнение заданий и остановить все пространства соответствующего экземпляра.

После аварийной остановки новые задания не должны запускаться до восстановления разрешённого режима работы.

### 19.5. Остаточные риски

Обычная контейнерная изоляция не считается эквивалентной изоляции виртуальной машины.

Сервис должен документировать остаточные риски исполнения недоверенного кода, особенно при размещении на устройствах с production-сервисами.

- [ ] Поддерживается управление Allowlist.
- [ ] Доступен журнал основных операций.

## 24. Контрольный сценарий ClipForge

Основным практическим критерием готовности Workspace является успешное выполнение сценария разработки ClipForge CLI.

Пользователь предоставляет ChatGPT исходный архив проекта и техническое задание.

ChatGPT самостоятельно создаёт пространство со следующими возможностями:

- base
- rust
- cpp
- git
- python
- ffmpeg
- whisper-vad

При необходимости запрашивается сетевой режим allowlist.

Внутри пространства выполняются:

- Проверка исходной сборки.
- Изучение исходного кода.
- Внесение изменений.
- cargo check.
- cargo fmt --check.
- cargo test.
- cargo clippy.
- cargo build --release.
- Интеграционная проверка FFmpeg.
- Интеграционная проверка Whisper.cpp VAD с совместимой моделью Silero.

Модель должна иметь возможность обнаружить ошибку компиляции, изменить исходный код и повторно запустить проверку.

В результате пользователь получает:

- Архив изменённых исходников.
- Отчёт о фактических результатах тестирования.
- Сведения об использованных версиях инструментов.
- Информацию об известных ограничениях.

Результаты невыполненных проверок должны быть обозначены явно.

Успешное выполнение проверок Linux не является подтверждением совместимости нативной Windows-сборки.

Контрольный сценарий должен выполняться через обычный веб-интерфейс ChatGPT с использованием Workspace MCP.

## 25. За пределами MVP

В версию 0.1.0 не входят:

- Распределённый кластер Worker.
- Удалённые вычислительные узлы.
- Нативные Windows-пространства.
- Podman и дополнительные контейнерные runtime.
- Firecracker и microVM.
- GPU-вычисления.
- Интеграция с Notify.
- Интеграция с приватными репозиториями GitHub.
- Интеграция с облачными файловыми хранилищами.
- Неограниченный публичный интернет.
- Полноценный браузер внутри пространства.
- Графический рабочий стол контейнера.
- Расширенный интерактивный терминал в веб-панели.
- Магазин сторонних модулей.
- Динамическая установка системных компонентов хоста.
- Публичный многопользовательский облачный сервис.
- Автономное управление языковой моделью.
- Собственный агентский runtime.

Перечисленные возможности могут рассматриваться после завершения и приёмки версии 0.1.0.
